# 无缝地图引擎 · 技术设计文档（方案 A）

> 目标：把当前「世界地图 ↔ 城市地图」两套跳转式系统，合并为一套**统一坐标系 + 连续 LOD** 的地图引擎——像高德/百度/谷歌那样，从星球一路滚轮缩放直到街道、建筑，中途不点击、不切换。
>
> 状态：**设计阶段，尚未实现**。本文基于对当前代码的实际调研，给出可落地路径、工作量与风险；不含运行时代码改动。
>
> 目标平台：Windows 便携版 + Android APK（两端共用 `site/`）。

---

## 1. 现状盘点（基于代码事实）

### 1.1 两套系统对比

| 维度 | 世界地图 | 城市地图 |
|---|---|---|
| 渲染技术 | Canvas 2D（`site/app/map.js`） | SVG（`site/city/city-map.js`） |
| 坐标系 | 星球网格 `(x, y)`，经度方向环绕 `W` | 城市局部公里坐标，经 `kx/ky` 换算 |
| 细节层级 | 4 级 `world/region/local/detail`，阈值 `<2.5 / <7 / <18 / ≥18` | 单套，缩放 `1 ~ 1800` |
| 缩放上限 | `fitScale × 48` | `1800` |
| 数据来源 | 程序化生成（地形/河流/边界/城市点位） | Worker 按需生成配方 `recipe`（街道/建筑/城墙/港口） |
| 进入方式 | 默认视图 | 点击城市 → 动态加载脚本 → 独立面板 |

### 1.2 关键发现：底层渲染器已经统一（可行性基石）

调研发现一个极其有利的事实——**两套系统的地形底图本就在共用同一个渲染器**：

- `site/core/render.js` 暴露 `R.render(req)`，接口是「按世界坐标窗口 `(x0, y0, s, w, h)` 渲染任意区域」。
- 城市配方的地形底图（`site/core/worker.js:505`）就是直接调用 `R.render({ x0, y0, s, w, h, ... })`，传入一个城市尺度的世界坐标窗口生成的。
- 城市内采样高程 `sampleElev(gx, gy, s, detail)` 也在同一渲染器内。

**结论**：分裂并不在"渲染内核"，而在上层三处：
1. **矢量要素层**：世界河流/边界/道路由 Canvas 绘制（`map.js`），城市街道/建筑由 SVG 生成（`city-map.js`）；
2. **坐标系单位**：世界用网格整数，城市用公里浮点（换算系数已知，见 §2.1）；
3. **调度方式**：城市细节由 Worker 按需生成并缓存（`urbanCache`，上限 24 座）。

这意味着方案 A 不是"从零重写"，而是**在统一渲染器之上，重建一层统一的矢量/细节调度层**——工作量从"重写引擎"降为"重构上层 + 扩展 LOD"。

### 1.3 坐标换算（统一坐标系的数学基础）

代码中已存在网格↔公里的换算：

```
cellKm = 2πR / W                    // 每个经度网格单元的公里数（R = 星球半径）
kx = cellKm × max(0.15, cos(lat))   // 城市局部 x 方向（经度，随纬度收缩）
ky = cellKm                         // 城市局部 y 方向（纬度）
lat = (90 - y / H × 180)°           // 由世界网格 y 反算纬度
```

`site/core/urban.js:15` 与 `site/core/citysite.js:170` 均已实现该换算。**统一坐标系可直接复用这套公式**，无需引入新的投影体系。

## 2. 目标架构

### 2.1 单一世界坐标系

定义全系统唯一的逻辑坐标系 **WGS（World Grid Space）**：

- 以现有世界网格 `(x, y)` 为基础（经度环绕 `W`，纬度 `0..H`）。
- 所有要素（地形、河流、边界、城市、街道、建筑）都用 WGS 坐标或"WGS + 缩放层级"表示。
- 城市局部公里坐标通过 §1.3 公式**双向映射**到 WGS，作为兼容层；城市配方内部的街道/建筑数据是相对城市中心的偏移，渲染时统一换算到 WGS。

### 2.2 连续 LOD 层级（从星球到建筑）

沿用并扩展现有 `levelOf` 阈值，形成一条连续尺度轴 `z`（相对缩放比）：

| 层级 | 缩放比 `zr` | 显示内容 | 数据源 |
|---|---|---|---|
| L0 星球 | `< 2.5` | 海陆、大洋、大陆、国家轮廓、都城点 | `R.render` 全图 |
| L1 区域 | `2.5–7` | +区域河流、省界、大城、山脉 | `R.render` 窗口 |
| L2 地方 | `7–18` | +地方道路、城镇、山峰海拔、湖湾 | `R.render` 窗口 |
| L3 城市群 | `18–48` | 城市点位放大为城区轮廓、主要街道骨架 | `cityTerrain` + 城区矢量 |
| L4 城区 | `48–200` | 城区路网、街区、城墙、港口 | Worker 城市配方（街区级） |
| L5 街道 | `200–800` | 街道、建筑轮廓、地块 | 城市配方（精细级） |
| L6 建筑 | `800–1800` | 屋顶材质、墙面纹理、城垛、街巷栅栏 | 城市配方（最高细节） |

**关键机制**：`R.render` 的窗口参数 `(x0, y0, s, w, h)` 天然支持任意尺度，L0–L2 直接复用；L3 是过渡带（城区轮廓开始出现）；L4–L6 复用城市配方，但把其公里坐标映射到 WGS 后绘制在同一画布。

### 2.3 渲染管线统一

```
                       ┌─────────────────────────────┐
  缩放/平移输入  ─────▶ │  统一相机 Camera(WGS)        │
                       │  - center(x,y), zoom z        │
                       └──────────────┬──────────────┘
                                      │ 按 z 决定可见层级集合
                       ┌──────────────▼──────────────┐
                       │  LOD 调度器 TileScheduler    │
                       │  - L0-L2: R.render 窗口瓦片  │
                       │  - L3-L6: 城市配方(按需生成) │
                       │  - 视口裁剪 + 缓存 + 预取     │
                       └──────────────┬──────────────┘
                                      │ 产出统一图元流
                       ┌──────────────▼──────────────┐
                       │  统一渲染层（单一 Canvas）    │
                       │  地形底图 + 矢量 + 注记       │
                       │  （SVG 细节层转为 Canvas 路径）│
                       └─────────────────────────────┘
```

- **SVG → Canvas**：城市细节层从 SVG DOM 改为 Canvas 路径绘制（保留现有 `city-map.js` 的几何生成逻辑，只替换"输出目标"）。理由：Canvas 与地形底图同层，才能做到无缝过渡与高性能；SVG DOM 在 L6 大量建筑元素下两端（尤其安卓）性能都吃紧。
- **瓦片化调度**：`R.render` 按视口切成瓦片异步生成（复用 `worker.js` 已有的条带渲染 `render(req)` 机制），避免一次性重绘全图。

### 2.4 数据层与缓存

- **城市配方缓存**：现有 `urbanCache`（LRU，24 座）扩展为二级缓存——WGS 网格块缓存（地形/低层矢量）+ 城市配方缓存（高层细节）。
- **预取**：缩放接近阈值时，提前 1 级生成目标瓦片（如从 L2 逼近 L3 时预生成城区轮廓），掩盖生成延迟。
- **渐进显示**：新层级未就绪时显示上一层放大图 + 淡入过渡，避免空白。

## 3. 双端性能预算

两端共用引擎，但预算差异大，LOD 上限与细节密度需分端配置。

| 项目 | Windows | Android |
|---|---|---|
| 目标帧率 | 60 fps | 30–45 fps |
| 最高层级 | L6（建筑，1800×） | L5（街道，约 800×）封顶 |
| 单帧 Canvas 图元上限 | ~50k | ~15k |
| 城市配方缓存数 | 32 | 8–12 |
| 瓦片渲染并发 | 4–6 Worker | 2 Worker |
| 纹理分辨率 | 原始 | 天体贴图降采样、禁用高倍墙面纹理 |
| 内存预算 | ~300 MB | ~120 MB |

分端配置通过构建时注入 `tools/build.mjs` 生成的 `dist/{platform}/` 差异文件实现（已有分端构建能力）。触摸缩放、惯性平移在安卓端优先优化。

## 4. 存档兼容

- 现有存档格式标记 `planet-forge-world`（schema/format 版本在 `world-package.js`）。
- **原则**：存档只保存"种子 + 生成设置 + 人物/标记/自定义库"，不保存渲染结果。因此升级引擎后重开存档会按新 LOD 重新生成——**老存档可打开，但视觉呈现会随新引擎变化**（与现有"重新打开世界会重新推演"的行为一致）。
- 城市布局存档（`.city.json`）目前绑定城市局部坐标；兼容方案是保留换算层，让旧布局按 §1.3 公式映射到 WGS 后继续可用。
- **不改动** `world-package.js` 的 schema/format 号（避免旧版本文件无法打开）；若新增字段，用可选字段向后兼容。

## 5. 分阶段实施（每阶段可独立验收）

| 阶段 | 交付 | 验收标准 | 估算 |
|---|---|---|---|
| P0 统一坐标层 | 封装 `wgs.ts/js`，实现网格↔公里双向映射，城市配方输出接入 | 城市地图可用 WGS 坐标渲染，与旧版视觉一致 | 3–5 天 |
| P1 单一相机 + 统一画布 | 移除独立城市面板，城市细节绘入主 Canvas | 点击城市不再跳转，原地放大即可见街道 | 1–2 周 |
| P2 LOD 调度器 | 三级瓦片调度 + 缓存 + 预取 + 渐进显示 | 从 L0 连续缩放到 L6 无卡顿、无空白 | 1–2 周 |
| P3 性能调优（双端） | 分端配置、图元裁剪、纹理降级 | 达成 §3 帧率与内存预算 | 1 周 |
| P4 回归与存档验证 | 全量测试、老存档/老布局兼容 | 现有测试通过，老存档可打开 | 3–5 天 |

**合计约 5–8 周**（熟练开发、单人全时）。这是核心引擎改造，建议每阶段结束单独提交并可回滚。

## 6. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| SVG→Canvas 改写工作量大、易出视觉偏差 | 高 | P0/P1 阶段用像素对比回归；保留 SVG 版作迁移参照 |
| L3→L4 过渡带细节断层 | 高 | 专门设计城区轮廓作为桥梁层，预取 + 淡入 |
| 安卓端高倍缩放性能不足 | 高 | 分端限制 L5 封顶、降纹理、减并发；真机尽早介入 |
| 城市配方按需生成延迟造成缩放卡顿 | 中 | 预取 + 渐进显示 + 缓存扩容 |
| 存档/布局兼容回归 | 中 | 保留换算层与 schema 不变，P4 专门验证 |
| 现有 14 项历史测试本就未适配 | 低（既有） | 不改核心生成算法；改造仅限渲染与调度层 |

## 7. 结论与建议

- **可行性**：高。底层 `R.render` 已是通用窗口渲染器，坐标换算公式已存在，城市配方已复用世界渲染器——方案 A 是"重构上层"而非"重写内核"。
- **代价**：约 5–8 周核心工程，属项目级重大改造，需分阶段推进、每阶段可回滚。
- **建议**：先执行 P0（统一坐标层）作为可行性验证——它能以最小改动证明"城市细节可用 WGS 渲染"，若 P0 视觉与性能达标，再继续 P1–P4；若不达标，及时止损转向方案 C（阈值自动淡入）。

> 本设计文档仅为方案，未改动任何运行时代码。确认方案后按 §5 分阶段实施。
